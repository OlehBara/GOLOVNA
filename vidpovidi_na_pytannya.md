# Відповіді на питання — розгорнуто і зрозуміло

---

## 1–20. Основи програмування та Python

**1. Транслятор — поняття та типи**

Транслятор — це програма, яка перетворює код, написаний людиною (Python, C, Java), у форму, яку може виконати комп’ютер. Без транслятора ми б писали машинний код із нулів і одиниць, що практично неможливо для великих проєктів.

Є три основні підходи. **Компілятор** перетворює весь файл одразу в окремий виконуваний файл (наприклад C → `.exe`). **Інтерпретатор** читає код рядок за рядком і одразу виконує (ранній Python, bash). **Транслятор у байт-код** (як у Python) спочатку робить проміжний файл `.pyc`, а потім його запускає віртуальна машина — це компроміс між швидкістю компіляції і гнучкістю інтерпретації.

---

**2. Байт-код — що це і навіщо**

Байт-код — це проміжна мова між вашим Python-кодом і машинними інструкціями. Коли ви запускаєте `python app.py`, інтерпретатор спочатку компілює файл у байт-код (зберігається в `__pycache__`), потім виконує його через Python Virtual Machine.

Навіщо це потрібно: повторний запуск швидший (байт-код уже готовий), один і той самий байт-код працює на Windows, Linux, macOS — потрібна лише встановлена Python VM для цієї платформи. Це не повна компіляція «в exe», але зручний і переносний варіант.

---

**3. Типізація в мовах програмування**

Типізація визначає, які дані можна зберігати в змінній і як мова реагує на помилки типів. Наприклад, не додати рядок `"5"` до числа без явного перетворення.

**Статична типізація** (TypeScript, Java) — перевірка до запуску програми; помилки видно в редакторі. **Динамічна** (Python, JavaScript) — тип визначається під час виконання. **Сильна** — мова не дозволяє «тихо» плутати несумісні типи; **слабша** — інколи робить неочікувані перетворення. Для великих проєктів статичні типи допомагають менше ловити баги в продакшені.

---

**4. PEP 8 — стиль коду Python**

PEP 8 — офіційний документ із правилами оформлення коду в Python, щоб усі читали чужий код однаково легко. Основні принципи: відступи **4 пробіли** (не табуляція), довжина рядка близько **79–99 символів**, пробіли навколо операторів `a + b`, `x = 1`, зрозумілі імена (`user_email`, а не `x`), порожній рядок між функціями і класами, імпорти згруповані (стандартна бібліотека → сторонні → локальні). Дотримання PEP 8 полегшує командну роботу і захист дипломного проєкту.

---

**5. Файл requirements.txt**

`requirements.txt` — текстовий список бібліотек і їх версій, без яких ваш Django-проєкт не запуститься (Django, psycopg2, gunicorn тощо). На новому комп’ютері або на сервері Render виконують `pip install -r requirements.txt`, і встановлюються ті самі пакети.

Вплив на запуск: без цього файлу з’являться помилки на кшталт `ModuleNotFoundError`. З файлом — однакове середовище у вас, у одногрупника і на продакшені, менше сюрпризів «у мене працює, а на сервері ні».

---

**6. List Comprehensions у Python**

List comprehension — стислий спосіб створити список з умовою в одному виразі: `squares = [x**2 for x in range(10)]` або з фільтром `[x for x in nums if x > 0]`. Це зручно і часто швидше за звичайний цикл `for`.

Особливості: читабельність падає, якщо вираз надто довгий — тоді краще звичайний цикл. Є також dict comprehension `{k: v for ...}` і set comprehension. У навчальних і дипломних проєктах використовуйте для простих перетворень, не для складної бізнес-логіки в одному рядку.

---

**7. Debugging (налагодження)**

Налагодження — це систематичний пошук і виправлення помилок у програмі. Роль у розробці величезна: без неї ви лише бачите «помилка 500», але не знаєте причину.

Методи: **логи** (`print`, `logging`), **breakpoint** у VS Code/PyCharm (зупинка на рядку, перегляд змінних), покрокове виконання, перевірка вхідних даних, відтворення бага в тесті. У Django ще корисні `DEBUG=True` з traceback і панель помилок. Раннє налагодження економить дні перед здачею проєкту.

---

**8. Області видимості та модель LEGB**

У Python змінна «видна» не всюди — це області видимості. Модель **LEGB** описує порядок пошуку імені:

- **L (Local)** — всередині поточної функції;
- **E (Enclosing)** — у зовнішній функції, якщо є вкладеність (замикання);
- **G (Global)** — на рівні файлу (модуля);
- **B (Built-in)** — вбудовані (`print`, `len`, `int`).

Якщо всередині функції написати `x = 10`, створюється локальне `x`, і глобальне не зміниться без `global x`. Розуміння LEGB допомагає уникати «чому тут None» і правильно використовувати замикання.

---

**9. Винятки (exceptions) у Python**

Виняток — це подія, коли під час виконання щось пішло не так (`ValueError`, `KeyError`, `DoesNotExist`). Програма може або впасти, або обробити помилку коректно.

Механізм: блок **`try`** — спробувати небезпечний код; **`except TypeError`** — що робити при конкретній помилці; **`else`** — якщо помилки не було; **`finally`** — виконати завжди (закрити файл, з’єднання з БД). У Django у views часто обгортають `json.loads` у try/except, щоб повернути зрозумілий JSON замість «білого екрану».

---

**10. Система контролю версій (VCS)**

VCS зберігає історію змін файлів: хто, коли і що змінив, можна повернутися до старої версії. **Локальні** — тільки на одному ПК (рідко). **Централізовані** (SVN) — один сервер, усі тягнуть звідти. **Розподілені** (Git) — у кожного повна копія історії.

Призначення в розробці: не втратити код, працювати в гілках (feature, fix), code review, відкотити зламаний деплой. Для диплому FinSmart Git показує етапи розробки і відповідальність кожного в команді.

---

**11. ООП — переваги і недоліки**

Об’єктно-орієнтоване програмування будує систему з **об’єктів**: у кожного є дані (атрибути) і дії (методи). Наприклад, об’єкт `Course` має `title`, `price` і метод `get_lessons()`.

**Переваги:** код ближчий до предметної області (курси, користувачі), повторне використання через класи й наслідування, зручніше підтримувати великі проєкти (Django моделі — це ООП). **Недоліки:** для скрипта на 20 рядків ООП зайве; можливе ускладнення (глибока ієрархія); не все в житті ідеально лягає в «об’єкт».

---

**12. Клас, __init__() і __del__()**

Клас — це шаблон (креслення), за яким створюють об’єкти. `user = User(name="Оля")` — конкретний об’єкт.

**`__init__(self, ...)`** — конструктор: викликається при створенні, задає початкові поля (`self.email = email`). Без нього об’єкт «порожній». **`__del__(self)`** — викликається перед знищенням об’єкта; рідко потрібен (закрити файл, з’єднання). У Django `__init__` моделі робить ORM, а `__del__` майже не використовують — краще context manager (`with`).

---

**13. Наслідування, інкапсуляція, поліморфізм**

**Наслідування** — дочірній клас отримує поля й методи батьківського. Приклад: `PremiumCourse` розширює `Course` додатковими полями. **Інкапсуляція** — приховування внутрішньої реалізації: зовні не чіпають `_balance`, доступ через методи. **Поліморфізм** — одна назва дії, різна поведінка: метод `save()` у різних моделях робить своє, але викликається однаково.

Разом це три кити ООП, на яких тримаються Django-моделі, форми і сервіси.

---

**14. Method Resolution Order (MRO)**

MRO — порядок, у якому Python шукає метод, якщо клас успадковує **кілька** батьків (множинне наслідування). Без MRO було б незрозуміло, чий `save()` викликати.

У Python 3 використовується алгоритм C3 — лінійний порядок без суперечностей. Подивитись можна: `ClassName.mro()`. На практиці множинне наслідування застосовують обережно; у Django частіше композиція (окремі класи-mixins), ніж складні «діаманти» наслідування.

---

**15. Контроль доступу до атрибутів**

Механізми в ООП і Python: **public** — звичайні поля, доступні всюди; **protected** — умовно «для нащадків», у Python позначають `_field` (домовленість, не жорстка заборона); **private** — `__field`, ім’я спотворюється інтерпретатором; **property** — `@property` для читання/запису з перевіркою (наприклад, не дати від’ємну ціну курсу). Це допомагає не ламати внутрішній стан об’єкта ззовні.

---

**16. Документування коду та PEP 257**

У Python документацію пишуть у **docstring** — рядок `"""..."""` одразу після `def` або `class`. Його бачить `help()` і автогенерація документації.

**PEP 257** вимагає: перший рядок — короткий опис одним реченням; далі, за потреби, деталі, аргументи, приклади; однаковий стиль у проєкті; англійською або узгодженою мовою команди. У дипломі docstring на ключових views і моделях показує акуратність і полегшує захист.

---

**17. База даних і СУБД**

**База даних** — організоване сховище даних у таблицях (користувачі, курси, замовлення). **СУБД** (MySQL, PostgreSQL, SQLite) — програма, що керує цими таблицями: зберігає, шукає, оновлює, забезпечує цілісність.

Роль в інформаційних системах: сайт без БД «забуває» все після перезавантаження. У FinSmart PostgreSQL/SQLite зберігає реєстрації, курси, кошик, прогрес — це серце backend.

---

**18. Вимоги ACID**

ACID — чотири властивості надійної **транзакції** в реляційній БД (набір операцій «все разом»).

**Atomicity (атомарність)** — або всі кроки виконались, або жоден (не зняти гроші без зарахування). **Consistency** — після транзакції дані відповідають правилам (баланс не від’ємний). **Isolation** — паралельні транзакції не плутають одна одну. **Durability** — після COMMIT дані збережені навіть при збої живлення. Для банківських і платіжних сценаріїв це критично; Django ORM транзакції підтримує через `atomic()`.

---

**19. Модель «сутність–зв’язок» (ERD)**

ERD — діаграма з **сутностями** (таблиці: User, Course) і **зв’язками** між ними (один-до-багатьох, багато-до-багатьох). Малюють на етапі проєктування, до написання коду.

Призначення: узгодити з замовником/командою структуру даних, уникнути «забули зв’язок кошик–користувач», спростити міграції Django. Для диплому ERD у пояснювальній записці показує системний підхід.

---

**20. Парсинг і скрейпінг**

**Парсинг** — розбір готових даних (HTML, JSON, XML) і витяг потрібних полів (заголовок курсу, ціна). **Скрейпінг** — автоматичний обхід багатьох сторінок і збір таких даних.

Особливості в сучасних застосунках: поважати `robots.txt` і умови сайту, не надсилати тисячі запитів за секунду, обробляти зміну верстки, використовувати затримки, інколи API замість скрейпінгу. У навчальних проєктах скрейпінг часто замінюють офіційним API або тестовими JSON.

## 21–40. Тестування, методології, математика

**21. Чи можливе 100% покриття тестами**

Теоретично можна наблизитись до високого відсотка покриття коду, але **стовідсоткове** тестування в реальності недосяжне і не завжди потрібне. Обмеження: неможливо перевірити всі комбінації вводу користувача; UI і інтеграції змінюються; тести самі можуть бути неправильними; написання й підтримка тестів коштують часу; деякі речі (зручність, дизайн) перевіряє лише людина.

Висновок: мета — **достатнє** покриття критичних місць (оплата, логін, запис на курс), а не гонка за 100%.

---

**22. Чому тестувати з ранніх етапів**

Помилку, знайдену на етапі вимог або дизайну, виправити в рази дешевше, ніж після релізу. Ранні unit-тести фіксують логіку (знижка, квіз), інтеграційні — зв’язок з БД. Це зменшує ризик «на тиждень до захисту все ламається». У Agile тестування вбудоване в кожен спринт, а не лише в кінці.

---

**23. Ручне vs автоматизоване тестування**

**Ручне** — тестувальник або розробник сам проходить сценарії: кнопки, форми, мобільна версія. Добре для UX, нових фіч, exploratory testing. **Автоматизоване** — скрипти (pytest, Selenium) повторюють перевірки без людини. Добре для регресії, API, стабільної логіки.

На практиці поєднують: автоматизація — «сітка безпеки», ручне — «чи зручно людині».

---

**24. Регресійне тестування**

Регресія — коли **нова** зміна зламала **старий** функціонал. Регресійне тестування перевіряє, що після оновлення все ще працює: логін, кошик, квіз, оплата.

Проводять після кожного значного коміту, перед релізом, після hotfix. У CI/CD автотести запускаються при push — це і є регресія в автоматичному режимі.

---

**25. Модульне (unit) тестування**

Unit-тест перевіряє **один маленький шматок** коду ізольовано: одну функцію, один метод, інколи один view з моками БД. У Django: `pytest` + `client.post('/add-to-cart/')`.

Роль: швидко знайти, де саме зламалось; дати впевненість при рефакторингу; задокументувати очікувану поведінку. Не замінює перевірку всього сайту разом (інтеграційні та e2e тести).

---

**26. Тест-кейс — визначення та структура**

Тест-кейс — формальна інструкція, **як** перевірити функцію. Структурні елементи: унікальний **ID**; **назва**; **передумови** (користувач залогінений); **кроки** (відкрити курс, натиснути «В кошик»); **очікуваний результат**; **фактичний результат**; **статус** (pass/fail). Для диплому тест-кейси в додатку показують системний підхід до якості.

---

**27. Тест-кейс vs чек-лист**

**Чек-лист** — короткий список пунктів «перевірити реєстрацію, кошик, квіз» без детальних кроків. Швидкий, гнучкий, залежить від досвіду тестувальника. **Тест-кейс** — детальніший, з чітким очікуваним результатом на кожен крок; відтворюваний будь-ким.

Чек-лист — для швидкого smoke-тесту перед демо; тест-кейс — для офіційної перевірки та звітності.

---

**28. Позитивне та негативне тестування**

**Позитивне** — «все правильно»: валідний email, коректний пароль, очікуємо успіх. **Негативне** — свідомо неправильні дані: порожнє поле, SQL-ін’єкція в рядок, клік без логіну — очікуємо зрозумілу помилку, а не падіння сервера.

Мета негативних тестів — стійкість і безпека; позитивних — що основний сценарій взагалі працює.

---

**29. Тестування граничних значень**

Перевіряють значення **на межі** допустимого діапазону: мінімум, максимум, мін−1, макс+1. Наприклад вік 17, 18, 150 для поля «повних років».

Найдоцільніше для числових полів, лімітів символів, кількості товарів у кошику, відсотків у квізі — саме на «краях» програмісти часто помиляються в умовах `if`.

---

**30. Що недоцільно автоматизувати**

Складна оцінка дизайну й зручності; разові перевірки; нестабільний UI, що змінюється щодня; сценарії, де підтримка автотеста дорожча за ручну перевірку; творчі exploratory тести; перевірка юридичних текстів «на смисл». Автоматизація — для повторюваного й стабільного, не для всього підряд.

---

**31. Переваги автоматизованого тестування**

Швидкість (сотні тестів за хвилини); повторюваність без втоми; запуск при кожному коміті (CI); менше людських помилок у рутині; раннє виявлення регресії; можливість тестувати навантаження (API). У довгостроковій перспективі економить час команди.

---

**32. Недоліки та обмеження автотестів**

Дорога початкова розробка і підтримка; flaky tests (падають без причини); не оцінюють «зручно чи ні»; складно покрити весь UI; хибне відчуття безпеки при поганих тестах; потрібні навички і інфраструктура. Автотести доповнюють, а не замінюють людину повністю.

---

**33. Етапи SDLC**

Життєвий цикл ПЗ (SDLC) зазвичай включає: **аналіз вимог** → **проєктування** (архітектура, БД) → **розробка** → **тестування** → **впровадження (деплой)** → **експлуатація і підтримка**. У класичному Waterfall етапи йдуть послідовно; у Agile (Scrum) — короткі цикли, повторення спринтів, постійний зворотний зв’язок від користувача.

---

**34. Ролі в Scrum-команді**

**Product Owner** — відповідає за цінність продукту, пріоритети беклогу («що важливіше — квіз чи оплата»). **Scrum Master** — допомагає процесу, знімає перешкоди, стежить за правилами Scrum (не «начальник» у класичному сенсі). **Developers** (розробники, тестувальники в команді) — створюють інкремент продукту за спринт. Усі разом відповідають за результат спринту.

---

**35. Daily Scrum**

Щоденна нарада до **15 хвилин**: кожен відповідає — що зробив вчора, що планує сьогодні, що **блокує** роботу. Мета — синхронізація, не вирішення всіх технічних проблем на місці (деталі — після). Обмежений час не дає перетворити зустріч на годинну планерку.

---

**36. Спринт у Scrum**

Спринт — фіксований період (зазвичай **1–4 тижні**), за який команда створює готовий інкремент продукту. Тривалість фіксована, щоб було передбачуване планування, ритм і звичка завершувати роботу, а не розтягувати задачу нескінченно.

---

**37. Sprint Planning**

На початку спринту команда з Product Owner обирає задачі з **product backlog**, оцінює обсяг і планує, **як** виконати (розбиття на підзадачі). Результат — **sprint backlog** і мета спринту. Мета планування — реалістична домовленість «що встигнемо за 2 тижні».

---

**38. Kanban vs Scrum**

**Kanban** — дошка з колонками (To Do → In Progress → Done), задачі йдуть **потоком**, без обов’язкових спринтів. **Scrum** — спринти, ролі, Daily, Review, Retrospective. Kanban гнучкіший для підтримки й дрібних задач; Scrum — для продуктової розробки з чіткими ітераціями. Відмінність: ритуали Scrum vs мінімум правил у Kanban.

---

**39. WIP limits у Kanban**

WIP (Work In Progress) limit — обмеження кількості задач у колонці «В роботі» (наприклад, не більше 3). Мета: не розпилюватись, швидше завершувати почате, побачити «вузьке місце» (зависли code review). Команда фокусується на закінченні, а не на старті 20 задач одночасно.

---

**40. Коли Waterfall ефективніший за Agile**

Каскадна модель (Waterfall) краща, коли **вимоги чіткі і рідко змінюються**: державні контракти, медичне ПЗ з сертифікацією, будівництво ПЗ «під ключ» з повною документацією заздалегідь. Там важлива передбачуваність і підписані ТЗ, а не щотижневі зміни пріоритетів. Для стартапів і навчальних веб-проєктів (як FinSmart) зазвичай зручніший Agile.

---

## 41–60. Математика, Bash, HTML, CSS

**41. Позиційний запис чисел**

У позиційній системі **значення цифри залежить від позиції**. У десятковій (основа 10) число 205 = 2×10² + 0×10¹ + 5×10⁰. У **двійковій** (основа 2) тільки 0 і 1 — зручно для комп’ютера. У **вісімковій** (8) і **шістнадцятковій** (16) — компактний запис для програмістів (кольори `#FF00AA`, права `chmod 755`). Одна й та сама ідея, різна «основа» системи.

---

**42. Перетворення між системами числення**

**З будь-якої системи в десяткову:** кожну цифру помножити на степінь основи (справа наліво позиції 0,1,2…) і додати результати. **З десяткової в іншу:** ділити число на основу, записувати **остачі**; остання остача — наймолодший розряд; читати остачі **знизу вгору**. Наприклад 13 у десятковій → у двійковій: 13÷2=6 ост.1, 6÷2=3 ост.0, 3÷2=1 ост.1, 1÷2=0 ост.1 → **1101**.

---

**43. Булева алгебра**

Булева алгебра працює з двома значеннями: **істина (1)** і **хиба (0)**. Вона описує логічні операції, які лежать в основі умов `if` у коді, пошуку в базах даних (`WHERE`), схем у процесорах і реле. Без неї важко проєктувати складну логіку перевірок (наприклад, «знижка, якщо студент І курс безкоштовний»).

---

**44. Базові логічні операції**

**І (AND)** — результат 1 лише коли **обидва** операнди 1. **АБО (OR)** — 1, якщо **хоча б один** 1. **НЕ (NOT)** — інверсія: 1 стає 0, 0 стає 1. У Python: `and`, `or`, `not`. У SQL: `AND`, `OR`. Таблиці істинності для двох змінних мають 4 рядки — усі комбінації.

---

**45. Закони булевої алгебри**

**Комутативність:** A∧B = B∧A. **Асоціативність:** групування не змінює результат. **Дистрибутивність:** A∧(B∨C) = (A∧B)∨(A∧C). **Закони де Моргана:** ¬(A∧B) = ¬A∨¬B. Практичне застосування — **спрощення** умов у коді й схемах: менше операцій, зрозуміліша логіка, менше помилок у складних `if`.

---

**46. Логічна функція та таблиця істинності**

Логічна функція залежить від входів (A, B, …) і дає один вихід. Її можна задати **формулою** або **таблицею істинності** — таблицею всіх комбінацій 0/1 і результату. Таблиця зручна для малої кількості змінних і перевірки, чи дві формули еквівалентні. У цифровій електроніці з неї будують схеми.

---

**47. Спрощення булевих виразів**

Мета — замінити довгий вираз коротшим без зміни сенсу. Переваги: простіша схема в «залізі», менше перевірок у коді, швидша робота, легше читати умову доступу. Інструменти: закони Буля, карти Карно (для невеликої кількості змінних).

---

**48. Множина, скінченні та нескінченні**

**Множина** — збір унікальних об’єктів (чисел, літер, користувачів). **Скінченна** — елементів можна порахувати (курси на сайті). **Нескінченна** — без кінця (всі натуральні числа). У програмуванні множини моделюють list, set, dict; операції ∪, ∩ мають аналоги у `set` в Python.

---

**49. Операції над множинами**

**Об’єднання** A∪B — елементи, що в A **або** в B. **Перетин** A∩B — тільки **спільні**. **Різниця** A\B — в A, але не в B. **Доповнення** — все з універсальної множини, чого нема в A. У SQL це схоже на JOIN, INNER/OUTER; у Python: `set(a) | set(b)`, `&`, `-`.

---

**50. Універсальна та порожня множина**

**Універсальна множина U** — «все, про що зараз говоримо» (всі студенти університету). **Порожня** ∅ — без жодного елемента. Доповнення A — це U без A. Порожня множина — підмножина будь-якої множини; важлива в доказах і в перевірках «чи є результат порожнім» у коді.

---

**51. Bash-скрипт**

Bash-скрипт — текстовий файл з командами для оболонки Bash у Linux/macOS (на Windows — WSL або Git Bash). Використовується для **автоматизації**: бекап БД, деплой, масове перейменування файлів, запуск Django після `git pull`. Перший рядок часто `#!/bin/bash`. Права: `chmod +x script.sh`, запуск `./script.sh`.

---

**52. Змінні в Bash**

Оголошення: `name="Іван"` (без пробілів навколо `=`). Звернення: `$name` або `${name}`. **Локальні** — тільки в скрипті або функції. **Змінні середовища** — `export PATH=...`, їх бачать програми, які скрипт запускає (наприклад `export DJANGO_SETTINGS_MODULE=...`). Лапки важливі: подвійні розкривають змінні, одинарні — літеральний текст.

---

**53. Bash і робота з файлами**

Типові прийоми: `[ -f file ]` — чи існує файл; `[ -d dir ]` — чи каталог; `cp`, `mv`, `rm`, `mkdir`; цикл `for f in *.txt; do ...; done`; читання рядків `while read line`. Перевірка прав перед видаленням, логування помилок — щоб скрипт не знищив дані випадково. У деплої — копіювання `static`, бекап `db.sqlite3`.

---

**54. HTML — роль у веб-сторінках**

HTML (HyperText Markup Language) задає **структуру** сторінки: заголовки, абзаци, посилання, форми, зображення. Браузер інтерпретує теги і будує DOM-дерево. HTML **не** відповідає за колір і верстку — це CSS. У Django HTML у шаблонах (`course_detail.html`) доповнюється даними з сервера.

---

**55. Структура HTML-документа**

`<!DOCTYPE html>` — оголошення HTML5. `<html lang="uk">` — корінь сторінки. `<head>` — службова частина: `<title>`, кодування UTF-8, підключення CSS/JS, meta для SEO. `<body>` — усе, що бачить користувач. Правильна структура важлива для доступності, SEO і валідаторів.

---

**56. Блочні vs рядкові елементи**

**Блочні** (`div`, `p`, `h1`, `section`) — зазвичай з нового рядка, на всю доступну ширину, можна задавати width/margin. **Рядкові (inline)** (`span`, `a`, `strong`, `img`) — у потоці тексту, не «ламають» рядок. У CSS `display: block/inline/flex` можна змінити поведінку. Для макету сайту FinSmart картки курсів часто в `div` (блок).

---

**57. Атрибути HTML**

Атрибут — пара **ім’я="значення"** у відкриваючому тегу. Приклади: `href` у `<a>`, `src` і `alt` у `<img>`, `class` і `id` для CSS/JS, `type` у `<input>`, `data-course-id` для своїх скриптів. Атрибути не показуються як текст на сторінці — вони налаштовують поведінку й стиль елемента.

---

**58. CSS — призначення**

CSS (Cascading Style Sheets) описує **вигляд**: кольори, шрифти, відступи, сітку, анімації. Один файл `style.css` може стилізувати весь сайт. Розділення HTML і CSS полегшує зміну дизайну без чіпання логіки шаблонів Django.

---

**59. Каскадність, специфічність, наслідування**

**Каскадність** — багато правил CSS можуть стосуватись одного елемента; застосовується «найсильніше» за правилами. **Специфічність** — inline style > #id > .class > тег. **Наслідування** — деякі властивості (color, font) дочірні елементи беруть від батька. Розуміння цього пояснює, чому «мій стиль не спрацював».

---

**60. CSS для макетів сторінок**

**display: flex** — гнучкий ряд або колонка (картки в ряд). **grid** — двовимірна сітка. **position: relative/absolute/fixed** — точне позиціонування (модальні вікна, шапка). У FinSmart flex/grid у каталозі курсів і profile; media queries — адаптив під мобільні. Без цих інструментів верстка «на таблицях» застаріла.
